
# GitHub Actions Custom Actions

## 1. What Is a Custom Action?

A custom action is a reusable piece of automation that you create for GitHub Actions.

Instead of repeatedly writing the same logic inside workflows, you can package that logic into an action.

Example:

```text
Workflow
   ↓
Custom Action
   ↓
Your automation logic
```

Custom actions can be created using:

- JavaScript
- Docker
- Composite Actions

---

## 2. Why Create Custom Actions?

Custom actions are useful when you have automation that you want to reuse.

Benefits:

- Reusable automation
- Less duplicate code
- Easier maintenance
- Consistent behavior
- Can be shared across repositories
- Can be published for others to use

---

## 3. Types of Custom Actions

There are three main types:

```text
Custom Actions
     │
     ├── JavaScript Action
     │
     ├── Docker Container Action
     │
     └── Composite Action
```

### JavaScript Action

Runs JavaScript/Node.js code.

### Docker Action

Runs inside a Docker container.

### Composite Action

Combines multiple existing steps.

---

## 4. `action.yml`

Every custom action needs metadata.

The main file is usually:

```text
action.yml
```

It describes:

- Action name
- Description
- Inputs
- Outputs
- Runtime
- Execution method

Example:

```yaml
name: My Custom Action
description: A simple custom action

runs:
  using: composite

  steps:
    - name: Hello
      run: echo "Hello from custom action"
      shell: bash
```

---

## 5. Basic Custom Action Structure

A simple local action can look like:

```text
.github/
    actions/
        hello/
            action.yml
```

The `action.yml` file contains the action definition.

---

## 6. Using a Custom Action

A workflow can use the local action:

```yaml
steps:
  - name: Run custom action
    uses: ./.github/actions/hello
```

GitHub will load the action from that directory.

---

## 7. Custom Action With Inputs

Inputs allow users to provide values to your action.

Example:

```yaml
name: Greeting Action
description: Prints a greeting

inputs:
  name:
    description: Name to greet
    required: true

runs:
  using: composite

  steps:
    - name: Greeting
      run: echo "Hello ${{ inputs.name }}"
      shell: bash
```

The workflow can provide:

```yaml
- name: Greeting
  uses: ./.github/actions/greeting
  with:
    name: Aayush
```

Output:

```text
Hello Aayush
```

---

## 8. Default Input Values

Inputs can have default values.

Example:

```yaml
inputs:
  name:
    description: Name
    required: false
    default: GitHub User
```

If no value is provided, the default value is used.

---

## 9. Outputs

A custom action can also return outputs.

Outputs allow information generated by an action to be used later.

Example:

```yaml
outputs:
  message:
    description: Greeting message
```

A composite action can set an output using:

```yaml
- name: Set message
  id: result
  run: echo "message=Hello GitHub" >> "$GITHUB_OUTPUT"
  shell: bash
```

The workflow can access the output through the action's output value.

---

## 10. JavaScript Actions

A JavaScript action uses Node.js to execute JavaScript code.

A simplified structure:

```text
my-action/
    action.yml
    index.js
    package.json
```

The main JavaScript file contains the action logic.

---

## 11. JavaScript Action Metadata

Example:

```yaml
name: JavaScript Action
description: Example JavaScript action

runs:
  using: node24
  main: index.js
```

The `main` property specifies the JavaScript entry file.

---

## 12. JavaScript Action Example

`index.js`:

```javascript
console.log("Hello from JavaScript Action!");
```

`action.yml`:

```yaml
name: JavaScript Action
description: Simple JavaScript custom action

runs:
  using: node24
  main: index.js
```

The workflow can then use:

```yaml
- name: Run JavaScript Action
  uses: ./.github/actions/javascript-action
```

---

## 13. Docker Actions

A Docker action runs its logic inside a Docker container.

Example structure:

```text
docker-action/
    action.yml
    Dockerfile
    entrypoint.sh
```

The Dockerfile defines the container environment.

The entrypoint script contains the execution logic.

---

## 14. Docker Action Metadata

Example:

```yaml
name: Docker Action
description: Example Docker action

runs:
  using: docker
  image: Dockerfile
```

GitHub builds and runs the action using the specified Docker configuration.

---

## 15. Composite vs JavaScript vs Docker

| Type | Main Technology | Best For |
|---|---|---|
| Composite | YAML + shell/actions | Reusing steps |
| JavaScript | Node.js | Custom program logic |
| Docker | Docker | Custom environments/dependencies |

Simple rule:

```text
Simple reusable steps → Composite

Custom Node.js logic → JavaScript

Special runtime/environment → Docker
```

---

## 16. Local vs Published Actions

A custom action can be stored inside your repository:

```yaml
uses: ./.github/actions/my-action
```

Or it can be published in a repository and used by others.

Example format:

```yaml
uses: owner/repository/path@version
```

Always check the action's documentation before using it.

---

## 17. Versioning Actions

When using an external action, you may see:

```yaml
uses: actions/checkout@v4
```

The `@v4` specifies a version reference.

For important production workflows, pinning dependencies to a specific commit SHA can provide stronger supply-chain protection than relying only on a moving branch or tag.

---

## 18. Security

Custom actions can execute commands with repository permissions.

Therefore:

- Don't hard-code secrets.
- Validate inputs.
- Avoid unsafe shell interpolation.
- Give workflows only required permissions.
- Review third-party actions before using them.
- Prefer trusted and maintained actions.
- Pin third-party actions appropriately for sensitive workflows.

Never expose secrets in logs.

Avoid:

```yaml
run: echo "${{ secrets.MY_SECRET }}"
```

## 19. Custom Action Example

Create:

```text
.github/actions/project-info/action.yml
```

Use:

```yaml
name: Project Info
description: Displays basic project information

inputs:
  project:
    description: Project name
    required: true

runs:
  using: composite

  steps:
    - name: Display project
      run: echo "Project: ${{ inputs.project }}"
      shell: bash

    - name: Display runner
      run: echo "Runner OS: $RUNNER_OS"
      shell: bash
```

Use it in a workflow:

```yaml
- name: Project Information
  uses: ./.github/actions/project-info
  with:
    project: GitHub-Mastery
```

## 24. Interview Questions

### Q1. What is a custom GitHub Action?

A reusable automation component created by a developer for GitHub Actions.

### Q2. What are the main types of custom actions?

- JavaScript
- Docker
- Composite

### Q3. What is `action.yml`?

The metadata file that defines how an action works.

### Q4. What is a composite action?

An action that combines multiple workflow steps into a reusable unit.

### Q5. When would you use a JavaScript action?

When custom Node.js logic is required.

### Q6. When would you use a Docker action?

When the action requires a specific containerized environment or dependencies.

### Q7. What are inputs?

Values supplied to an action by the workflow.

### Q8. What are outputs?

Values produced by an action that can be consumed by later steps or jobs.

### Q9. Why is action versioning important?

It helps control changes and makes workflow dependencies more predictable.

### Q10. Why is security important for custom actions?

Actions execute automation within workflows and may have access to repository resources and permissions.
